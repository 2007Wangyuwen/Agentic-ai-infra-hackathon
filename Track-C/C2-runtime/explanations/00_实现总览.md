# AEC-C2 Runtime 实现总览

本文档解释本提交在 C2 赛题中的整体实现思路、文件分工、执行路径、评分覆盖和提交方式。

## 1. 赛题目标

C2 要求实现 AEC 虚拟 GPGPU 的 Host Runtime，最终核心提交物是：

```text
libaec.so
agents/dma_agent.py
agents/kernel_agent.py
```

其中 `libaec.so` 必须导出 `include/aec_runtime.h` 中声明的全部 C ABI 符号。Runtime 需要支持设备查询、错误处理、设备内存管理、同步/异步 DMA、Stream/Event、Kernel Launch、GEMM 和向量计算库等功能。

本题的关键约束是：成功的 `aecLaunch` 和计算库接口不能在 Host 侧直接计算结果，而必须：

1. 解析官方固定 kernel image。
2. 生成 little-endian canonical 参数块。
3. 构造 `aecDeviceCommand`。
4. 通过 `aecDeviceSubmit` 提交给官方 `libaec_device.so`。
5. 由受控虚拟设备解释 AEC image 并产生结果、虚拟周期和 trace 证据。

因此，本实现的核心原则是“Host Runtime 只做调度、校验和 ABI 封装，实际计算交给官方设备库”。

## 2. 涉及文件



### `src/aec_runtime.cpp`

这是 Runtime 的主体实现，编译后生成 `libaec.so`。

主要负责：

- 实现 `aec_runtime.h` 中所有公开 API。
- 维护 Runtime 侧的 allocation、stream、event、registration 等生命周期状态。
- 把同步/异步 copy 转换成 DMA device command。
- 把 `aecLaunch` 和计算库 wrapper 转换成 ISA launch device command。
- 统一处理错误码映射、统计查询和 fault 后恢复。



### `agents/dma_agent.py`

这是 Excellent 阶段的 DMA 策略 Agent。

主要负责：

- 从 stdin 读取一次 JSON 请求。
- 枚举所有合法 DMA 策略组合。
- 根据赛题给出的虚拟周期公式选择最小周期方案。
- 向 stdout 输出唯一 JSON，不输出日志。



### `agents/kernel_agent.py`

这是 Excellent 阶段的 Kernel image 策略 Agent。

主要负责：

- 从 stdin 读取一次 JSON 请求。
- 在输入提供的 candidates 中过滤合法 image。
- 根据 workspace、alignment、divisibility 和可选 `diagnostic_cycles` 选择 image。
- 输出一个合法的 `kernel_id`。



### `ORIGINALITY.md`

这是原创性与依赖声明草稿。

主要说明：

- 使用官方 starter kit 的边界。
- Runtime 和 Agent 是本提交实现。
- 没有额外第三方依赖。
- 披露使用大语言模型辅助开发。
- 声明未修改官方评测组件，未硬编码隐藏测试，未 Host 侧绕过计算路径。



### `submission/`

这是最终提交目录，由构建后复制生成。

当前应只包含：

```text
submission/
├── libaec.so
└── agents/
    ├── dma_agent.py
    └── kernel_agent.py
```

不要把官方 `libaec_device.so`、`include/`、`kernels/`、`grader/` 放入正式提交目录，除非平台另有说明。

## 3. 实现分层

本实现可以分为四层：

### 第一层：公开 C ABI

所有 `extern "C"` 函数都按照 `aec_runtime.h` 暴露，例如：

- `aecDeviceCount`
- `aecAlloc`
- `aecCopyH2D`
- `aecStreamCreate`
- `aecEventRecord`
- `aecLaunch`
- `aecMatmulF32`
- `aecAxpy`
- `aecDot`
- `aecNrm2`

这一层负责接收用户调用，并把错误通过 `finish()` 写入线程局部 last error。

### 第二层：Runtime 状态管理

Runtime 内部维护以下状态：

- `allocations`：记录 live device allocation 的 base 和 bytes。
- `registrations`：记录 host registered memory interval。
- `live_streams`：记录当前有效 stream handle。
- `live_events`：记录当前有效 event handle。
- `next_sequence`：为 device command 分配严格递增 sequence。
- `next_dma_channel`：在两个 DMA channel 之间轮转。

这些状态只用于 Runtime API 生命周期管理，不保存真实设备内存内容。

### 第三层：Command 构造

同步/异步 copy 构造成：

```text
AEC_DEVICE_OP_H2D
AEC_DEVICE_OP_D2H
```

Kernel 和计算库构造成：

```text
AEC_DEVICE_OP_ISA_LAUNCH
```

所有 command 都设置：

- ABI version。
- sequence。
- stream id。
- DMA src/dst/host address/bytes。
- kernel handle。
- ISA version。
- entry PC。
- grid/block。
- canonical parameter bytes。



### 第四层：官方设备执行

最终所有实际工作通过：

```cpp
aecDeviceSubmit(&command, &completion)
```

提交给官方 `libaec_device.so`。完成后读取 completion status，并映射为 Runtime 错误码。

## 4. 为什么符合规则



### 不硬编码测试

代码没有根据 `case_id`、文件名、输入 hash、公开测试名称、隐藏测试标识等做分支。

Runtime 的行为基于：

- API 参数。
- allocation/registration 生命周期状态。
- 赛题公开 ABI。
- fixed kernel manifest 的通用约束。

Agent 的行为基于：

- 请求中的 bytes/alignment/registered/concurrency。
- candidates 中的 workspace/alignment/divisibility/variant。
- 输入中提供的 diagnostic cycles。



### 不绕过评测

计算接口没有直接在 Host 侧实现矩阵乘法或向量运算结果，而是构造官方参数块并提交 fixed image。

公开评分中的计算项会检查：

- `isa_launches`
- `instructions_retired`
- `last_kernel_handle`
- `last_trace_digest`

当前实现能够通过这些证据检查。

### 不修改官方组件

提交实现只修改/生成自己的：

- `src/aec_runtime.cpp`
- `agents/dma_agent.py`
- `agents/kernel_agent.py`
- 文档文件

没有修改官方 header、device library、kernel image、grader、schema 或测试定义。
